## Commands

```bash
npm run dev      # dev server (Turbopack)
npm run build    # production build — forced to webpack, see note below
npm run start    # serve the production build
npm run lint      # eslint (eslint-config-next: core-web-vitals + typescript)
npx tsc --noEmit  # type check only, no separate script defined
npm test          # vitest — 62 tests, all in lib/engine/reducer.test.ts

# one test / one describe block, by name substring:
npx vitest run -t "weekly cap"
npx vitest --watch          # watch mode while iterating on the engine
```

Before any commit, the full gate is: `npm test && npx tsc --noEmit && npx eslint . && npm run build`.

### Verifying UI changes — use the preview harness

The authenticated UI **can** be driven in a browser without Supabase, and
should be, because `npm run build` succeeding only proves it compiles:

```bash
PREVIEW_MODE=1 PORT=3111 npm run start   # then drive http://127.0.0.1:3111/preview
```

`/preview?scenario=fresh|seasoned|reloaded` renders the **real** Status Window
(`components/PreviewHarness.tsx`) against in-memory fixtures, with the write
surface swapped for stubs via `components/ActionsContext.tsx`. It is
double-gated — `app/preview/page.tsx` calls `notFound()` and `proxy.ts`
refuses to make the path public — unless `PREVIEW_MODE=1`, which production
never sets. Confirmed as production: `GET /preview` → 307 `/login`, no
harness content in the body.

`scenario=reloaded` exists specifically to reproduce **post-hard-reload
hydration**: DB-shaped rows only (uuid ids, PostgREST `+00:00` timestamps),
no client-optimistic events. Bugs have hidden in that gap before.

What the harness does **not** cover, and what still needs a real deployment:
the Server Actions themselves — auth, RLS, the weekly XP cap, the daily
double-completion guard, and **anything cache-related** (Next's Data Cache
behaves differently on Vercel). Anything touching `*.supabase.co` is
unreachable from a sandbox.

When a browser check fails, **diagnose before "fixing"**. The suite's first
run reported six failures and all six were bugs in the test, not the app
(a `CountUp` read mid-animation; assertions that contradicted deliberate
design). Never weaken an assertion to force a pass.

Two failure modes this harness is structurally blind to, both of which
reached production and cost multiple QA rounds — check them by eye:
- **Contrast.** `innerText` assertions pass on text nobody can see. An
  `--color-ink-faint` toast on the near-black background was invisible for
  three QA passes while the test called it a PASS.
- **Tap-target size.** The harness clicks by selector and never misses;
  humans and click-driving agents miss small targets. Keep interactive
  targets ≥44px in this phone-first app.

**Build is forced to webpack** (`next build --webpack` in package.json).
Turbopack has documented `NEXT_PUBLIC_*` env-var inlining regressions on
Vercel's build pipeline (Next.js 15.3+, notably under the standalone-output
packaging path); `next dev` is unaffected and stays on Turbopack.

Requires `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (see
`.env.local.example`). No service role key needed anywhere in this repo — every
table is RLS-scoped to `auth.uid()`, so the anon key plus a user's session is
sufficient. See `db/README.md` for applying the schema/policies to a fresh
Supabase project.

## Architecture

**Phase 1 in progress** — see `DESIGN.md` (canonical product spec) and
`AGENTS.md` (the short version: covenant, tone, AI boundary, life model,
design invariants). Phase 0's fake data (`lib/data.ts`) is gone; auth, the
database, and real progression are wired. Not yet built: the AI Induction
interview (deferred pending a provider decision — see the AI boundary in
`AGENTS.md`), vices, Measures, seasons — all Phase 2+ per `DESIGN.md`.

### Migrations must be applied by hand

`db/migrations/` is generated by `npx drizzle-kit generate`; **nothing applies
it automatically**. Migrations `0001`–`0003` are run manually in the Supabase
SQL editor — use `db/APPLY.sql`, which bundles them idempotently. A deploy
whose queries name a column from an unapplied migration is the single most
common failure mode in this repo — it presents as "my data vanished".
`app/page.tsx` now surfaces that as a `[ FAULT ]` panel naming the error
instead of rendering an empty character.

**`drizzle-kit` does not generate RLS.** A new table is unprotected until
policies are written by hand into `db/policies.sql` (see the `epics` block) and
run separately.

### Database reads must never be cached — this broke production once

`supabase-js` issues its REST calls through `fetch()` with no cache directive,
which leaves Next's Data Cache free to **memoize the event log**. In an
event-sourced app the character *is* the log, so a cached read renders a
character that is quietly, confidently wrong — the worst possible failure for
a product whose whole premise is that the record is true.

It happened: the live Status Window served stale totals across genuine hard
reloads, and `undoCompletion`'s own read couldn't see a completion committed
minutes earlier, so it refused and wrote nothing. Now enforced at both layers:

- `lib/supabase/server.ts` wraps the client's `fetch` with `cache: "no-store"`
  — covers Server Components **and** Server Actions, every query.
- `app/page.tsx` additionally exports `dynamic = "force-dynamic"` and
  `fetchCache = "force-no-store"`.

**Never remove either, and never add a cached read path to this data.** If a
number on screen disagrees with the database, suspect caching first.

### The progression engine (`lib/engine/`) — read this before touching XP/level/Integrity anywhere

This is the one part of the app the AI boundary applies to literally: nothing
here may depend on network I/O, randomness, or an LLM, and `reducer.test.ts`
statically greps `reducer.ts`, `rules.ts`, `chronicle.ts`, `titles.ts` and
`requisites.ts` for exactly that on every test run. The check is real — it once
failed because a *comment* named the forbidden random call.

- **`events.ts`** — `SystemEvent`, a closed union of five shapes
  (`quest_completed`, `claim_verified`, `claim_declined`, `claim_retracted`,
  `completion_retracted`). This is the append-only log — never store a
  computed total, store what happened. `completion_retracted` is the misclick
  undo: the reducer voids the referenced `quest_completed` entirely (XP,
  domain gain and weekly-cap usage all replay as if the tap never happened),
  whereas `claim_retracted` is an honesty admission that refunds nothing.
- **`reducer.ts`** — `reduce(events, now)` is a pure function that replays the
  log into a `CharacterState` (level, XP, Integrity, domains, tier). The
  **same function runs on the client and the server**: the client appends an
  optimistic event and re-runs `reduce()` for instant, exactly-correct UI
  feedback, while a Server Action persists the real event. This is not a
  duplicated implementation — it's the same module imported in both places, so
  there's no way for the two to drift.
- **`rules.ts`** — every tunable number (`XP_BY_DIFFICULTY`, the weekly XP
  cap, the level curve, decay rates, tier thresholds, `TIER_NAMES`). Isolated
  here on purpose so a future move to DB-backed, versioned config rows (Phase
  2, "balance tweaks must not require a deploy") is a relocation, not a
  rewrite.
- **`domains.ts`** — `DomainKey`, `DOMAIN_KEYS`, and `DOMAIN_DISPLAY` (label/
  colour/description). Deliberately independent of the old `lib/data.ts` —
  the engine never depended on Phase 0's fake data, and now nothing does.
- **`chronicle.ts`** — the System's voice, v1: the log rendered as journal
  lines, the Real-World Ledger, and the day/week reports behind the close-out.
  Deliberately XP-number-free in journal lines (a capped completion's nominal
  value would be a wrong number). `buildDayReport` computes today's XP as the
  **difference of two full replays**, never nominal arithmetic, so a capped day
  honestly reports 0.
- **`titles.ts`** — earned, cosmetic titles with deterministic conditions.
  `kind: "level"` shows its requirement while locked (goal gradient);
  `kind: "hidden"` shows only `???` until earned (discovery).
- **`requisites.ts`** — preparation as a gate (`DESIGN.md` → "Requisites").
  Materials are a **readout of the raw domain stat**, never a currency: never
  spent, traded, or decayed, because a spendable material would make a
  milestone purchasable. `evaluateRequisites` only ever **reports** — it
  cannot withhold XP, and a locked milestone always stays claimable.

Randomness lives in **`lib/loot.ts`, deliberately outside `lib/engine/`**: the
roll happens once server-side and the *result* is stored on the event, so
replay stays deterministic and the engine keeps passing its purity check.

### Data flow: Server Component → Client Component → Server Actions

- **`app/page.tsx`** — async Server Component. Gets the authenticated user,
  upserts their `profiles` row (first-visit bootstrap — no Induction yet, so
  everyone starts at Level 1 / all domains at 0, which is correct per "Level 1
  must feel weak"), fetches `quests` and `event_log`, maps rows to
  `SystemEvent[]` via `db/mappers.ts`, and renders `StatusWindowClient`.
- **`components/StatusWindowClient.tsx`** — owns all interactive state.
  Mirrors Phase 0's animation choreography (optimistic update → toast → check
  for a level/tier crossing → overlay) but every number now comes from
  `reduce()` over real events, not ad-hoc arithmetic. On a Server Action
  failure, it reverts the optimistic event by id and surfaces
  `[ REJECTED ] <reason>` via the same toast mechanism used for XP gains.
  Two client-side patterns in here are load-bearing, both born from real
  production failures — keep them for any new action call:
  - **`safeCall(busyId, fn)`** wraps every awaited action. A Server Action can
    *throw* (network drop, deploy mid-flight), not just return `{ ok: false }`;
    an uncaught throw would strand `busy` forever, after which every tap
    silently returns early and the whole app reads as dead. `safeCall` always
    clears `busy` in `finally` and turns a throw into an ordinary rejection.
  - **`resync()`** runs after every *successful* mutation (`router.refresh()`
    in production, a no-op in the harness). An adoption effect then folds the
    fresh server rows into client state, gated on a `busyRef` so it can never
    clobber an in-flight optimistic update with stale props. This is what makes
    client/server drift self-healing rather than permanent.
- **`components/ActionsContext.tsx`** — components call `useActions()` rather
  than importing Server Actions directly, so the preview harness can inject
  stubs. The **default is the real action set**; no server-side check can be
  weakened by it, because the checks live in `app/actions.ts`.
- **`app/actions.ts`** — the entire write surface for progression
  (`completeQuest`, `undoCompletion`, `verifyClaim`, `declineClaim`,
  `createQuest`, `createEpic`, `chooseTitle`, `setCharacterName`, `signOut`).
  Every action re-derives the acting user from the session server-side; never
  trusts a client-supplied `user_id`. `completeQuest` explicitly refuses
  `weighty` quests — those must go through `verifyClaim`/`declineClaim`.
  `undoCompletion` (the misclick undo) never deletes — it appends a
  `completion_retracted` event that the reducer voids the original against,
  and it refuses weighty quests: a verified claim exits only via
  `claim_retracted` at the seasonal audit, which refunds nothing.
  Anything derived from the log (title entitlement, whether a claim was
  `unprepared`) is **re-derived server-side**, never trusted from the client.
  A client-supplied `epic_id` is verified to belong to the acting user.
  Client-supplied timezone offsets are clamped to ±14h.
- **`proxy.ts`** — refreshes the Supabase session on every request and gates
  everything except `/login` and `/auth/*`. Named `proxy.ts`/`proxy()`, not
  `middleware.ts`/`middleware()` — Next.js 16 renamed the convention, and a
  leftover `middleware.ts` is silently ignored (no error, no warning) once a
  Next version fully drops the old name, which would kill the entire auth
  gate with nothing surfacing it. Deliberately added in a later commit than
  the login page itself — flipping the gate on before `/login` was proven to
  reach Supabase would have broken the live site behind a wall nobody could
  get through.

### Database (`db/`)

- **`schema.ts`** — Drizzle schema, used for migration generation only;
  nothing at runtime queries through Drizzle. All runtime reads/writes go
  through `@supabase/supabase-js`, which returns raw **snake_case** column
  names — `db/mappers.ts`'s `EventRow`/`QuestRow` types reflect that
  deliberately, not the camelCase Drizzle would produce.
- **`policies.sql`** — RLS **and grants**. `event_log` gets `INSERT`/`SELECT`
  policies and **no `UPDATE`/`DELETE` policy for any role**, including the
  row's own owner — that omission is what makes the honesty system's audit
  trail provable. `quests` allows delete only while `status = 'active'`.
  `UPDATE` is granted **per column**, not table-wide (`quests`: `status`,
  `completed_at`; `profiles`: `character_name`, `title`): Server Actions run
  with the user's own JWT, so RLS cannot tell them from a hand-rolled
  PostgREST call, and a table-wide grant let a client raise `difficulty`
  before completing, clear `weighty` to skip verification, or null
  `requisites`. Verified against a real Postgres that all four attacks return
  `permission denied` while the legitimate write succeeds.
- **`APPLY.sql`** — every migration after `0000` plus the `epics` RLS, as one
  idempotent paste for the Supabase SQL editor, ending in queries that print
  what landed. This is what to hand someone when the app reports a missing
  column.
- **`mappers.ts`** — `rowToEvent()` bridges a raw `event_log` row to the
  `SystemEvent` union; throws on an unrecognized `type` rather than silently
  dropping it.
- **`README.md`** — how to apply the schema/policies to a fresh project, and
  how the policies were behaviourally verified (real local Postgres, stub
  `auth.uid()`, two simulated users) before ever reaching production.

### Auth (`lib/supabase/`, `app/login/`, `app/auth/callback/`)

Two passwordless routes: **magic link** (`signInWithOtp`) and **Google OAuth**
(`signInWithOAuth`, provider configured in the Supabase dashboard). Both land
on `app/auth/callback/route.ts`, whose `exchangeCodeForSession` handles the
OTP and PKCE flows identically — adding a provider needs no route changes.
`lib/supabase/client.ts` / `server.ts` are the standard `@supabase/ssr`
browser/server split (see the caching note above for `server.ts`).
`app/login/page.tsx` is styled in the System's voice, not a generic form.

Supabase's **Site URL and Redirect Allowlist** must name the deployed origin,
or confirmation emails send users to a dead `localhost`.

### `app/layout.tsx` / `app/globals.css`

Unchanged from Phase 0. Three fonts via `next/font` mapped to
`--font-display` / `--font-sys` / `--font-body`; the entire design system
(palette, easing, named `.animate-*` classes tied to specific `@keyframes`)
lives in `globals.css` as a Tailwind v4 `@theme` block. New UI should reuse
these tokens rather than introducing new colours or one-off transitions.
`prefers-reduced-motion` is handled globally there.

### Components (`components/`)

- **`Panel.tsx`** — the System-window shell used for every panel: the
  delayed scan-in reveal, the bracket-corner frame, the `"panel"` sound cue
  on reveal. Build new panel-like UI as children of this, not a bespoke `<div>`.
- **`CountUp.tsx`** — animated tabular-number counter; reads
  `useReducedMotion()` to skip animation and render the raw value instead.
- **`StatBar.tsx`** — a domain bar. `trend` is optional and only rendered
  when present — showing a fabricated "+0" before seasons (Phase 2) exist
  would be exactly the "confidently wrong number" `DESIGN.md`'s Measures
  section warns against, so `app/page.tsx` doesn't pass one yet.
- **`Avatar.tsx`** — still the Phase-0 placeholder silhouette (real
  illustrated tiers are Phase 2). The figure stays System-cyan regardless of
  dominant domain; only the aura glow takes the domain colour. `decay` prop
  now driven by real `daysAbsent` from the reducer.
- **`LevelUpOverlay.tsx`** / **`TierUpOverlay.tsx`** — both implement the
  "beat of silence before the reveal" sequencing. `TierUpOverlay` no longer
  hardcodes a day count ("Earned across 187 days" was Phase 0 flavour text
  that became a fabricated number once real data existed — removed).
- **`VerificationScreen.tsx`** — the honesty-system UI. Only for `weighty`
  quests. Opens with the parent epic's name and the player's own stated
  intent, then any **requisites** with exact shortfalls. Unmet requisites
  never disable the claim — the button becomes `I DID IT ANYWAY` and pays
  in full. The System cannot see your life and must not assert authority
  over it.
- **`RecordOverlay.tsx`** — a broken personal record. States the fact and the
  number it beat, nothing more; `previous: 0` reads as "you have not done this
  before" rather than a fabricated comparison.
- **`EpicsPanel` / `ChroniclePanel` / `TitlesPanel` / `FirstRunRite`** — the
  campaign layer, the Ledger + journal, earned nouns, and the day-one identity
  beat (name → Oath → cold opening statement) that stands in until Induction
  exists.

### Sound, haptics, and external state (`lib/`)

- **`lib/sound.ts`** — all audio synthesized with the Web Audio API; no audio
  files in the repo. Mute state is **not** React state — it lives in a small
  module-level store (`subscribeMuted`/`isMuted`/`setMuted`), because
  mirroring `localStorage` into `useState` via an effect trips ESLint's
  `react-hooks/set-state-in-effect` rule and fails the build.
- **`lib/haptics.ts`** — `navigator.vibrate` patterns, gated by the same mute
  flag from `lib/sound.ts`.
- **`lib/hooks.ts`** — `useMuted()` and `useReducedMotion()`, both via
  `useSyncExternalStore`. The pattern to follow for any future external state.

### Conventions

- Path alias `@/*` → repo root (`tsconfig.json`).
- `.tnum` class on any number that animates, so tabular figures don't
  jitter — `CountUp` already applies it.
- `data-testid` on anything a test/automation script needs to drive.
- Never write to `event_log` from anywhere except `app/actions.ts`. Never let
  an AI-touched code path write XP, level, or Integrity — see the AI boundary
  in `AGENTS.md`.

## #LESSONS

- **Test the invariant, not the nearby number.** The weekly-cap test asserted
  `totalXp` and passed for months while capped completions still raised domain
  stats — the covenant's anti-farming rule was broken in a way 55 unit tests and
  70 browser assertions all missed. When a rule says "X cannot be farmed", assert
  it against *every* quantity X feeds, not just the headline one.
- **Server Actions hold no more authority than the browser.** They run with the
  signed-in user's own JWT, so RLS cannot distinguish `app/actions.ts` from a
  hand-rolled PostgREST call. Any rule enforced only in an action is advisory
  until the grant or policy enforces it too — grant UPDATE per column.
- **Diagnose a failing check before touching it.** Of the browser suite's first
  seven failures, six were the test's fault and one was a wrong fixture in my own
  fix. Weakening an assertion to get green would have buried a real defect.
- **A triple-zero symptom means the input never happened.** Three QA passes
  chased an UNDO "bug" showing no toast, no network call, no DB write, and no
  console error — a combination no code path could produce, since every branch
  emits UI feedback before or regardless of the server. The click was missing a
  ~24px target. When remote-driven QA reports impossible symptoms, verify the
  input mechanism (DOM-dispatched `.click()`) before debugging the stack — and
  keep tap targets ≥44px in a phone-first app so precision never matters.
- **"Rendered" is not "visible".** The same investigation's other dead end was a
  toast that fired correctly every time in `--color-ink-faint` on the near-black
  background. DOM-text assertions passed; humans and screenshots saw nothing, so
  three passes logged it as a silent no-op. Assert contrast, or eyeball it.
- **Cached reads make an event-sourced app lie.** `supabase-js` uses bare
  `fetch()`, so Next happily memoized the event log — the character rendered
  stale across hard reloads and a Server Action's own read couldn't see a
  just-committed row. Derived-from-log data must be `no-store` everywhere.
- **The harness and the live app can fail in opposite directions.** Stubbing the
  write surface made client/server desync structurally invisible to 62 unit
  tests and 70 browser assertions; it took a human driving the real deployment
  with SQL in the other hand to find it. Keep the loop: harness for logic,
  live pass for truth.
